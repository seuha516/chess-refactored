# 아키텍처

## 원본의 구조와 문제

원본(`chess-js`)은 서버가 거의 **중계기**였습니다.

- 규칙 판정, 시간 계산, 체크메이트·무승부 판정, 50수·동형 반복 계산을 모두 각 클라이언트(`static/js/Chess.js`,
  약 2,900줄의 전역 변수 기반 코드)가 했고, 서버(`app.js`)는 받은 이벤트를 그대로 다른 소켓에 전달했습니다.
- 각 클라이언트가 자기 시점으로 뒤집힌 좌표의 보드를 따로 들고 있어서, 좌표 변환(`7 - x`)과 이벤트 순서에
  상태 일관성이 달려 있었습니다.
- 그 결과 클라이언트가 보낸 `gameend`(승자·사유 임의 지정), `movefinish`(아무 좌표), `kill`, `starttimer` 등을
  서버가 검증 없이 받아들였고, 두 플레이어가 동시에 나가면 좌석이 영구히 점유되어 서버를 재시작해야 했습니다.

이 문제들은 `369ed99` 커밋의 특성화 테스트로 재현한 뒤 고쳤습니다.

## 현재 구조

```
┌────────── 브라우저 ──────────┐          ┌──────────────────── 서버 인스턴스 ────────────────────┐
│ main.ts  로비/방 전환, 요청   │  요청 →  │ app.ts      Socket.IO 연결, 검증, 요청 제한, 보안 헤더 │
│ view-model.ts 스냅샷 → 화면  │ ← 스냅샷 │ service.ts  세션·로비·방 입장, 접속 기록, 타이머, 방송  │
│ board-view.ts 보드 입력      │          │ logic.ts    방 상태 전이(순수 함수)                    │
│ shared/chess, clock  표시용  │          │ shared/chess, clock  판정의 기준                        │
└──────────────────────────────┘          └───────────────┬───────────────────────────────────────┘
                                                          │ Store (store.ts)
                                           MemoryStore(로컬·테스트) / RedisStore(여러 인스턴스, Vercel)
```

- **서버가 유일한 진실의 원천**입니다. 클라이언트는 "이 수를 두고 싶다" 같은 *요청*만 보내고, 서버는 규칙 엔진으로
  검증한 뒤 방의 전체 상태 스냅샷(`RoomSnapshot`, 채팅 포함)을 그 방의 모든 접속자에게 보냅니다. 클라이언트는
  스냅샷을 그대로 그리므로 상태가 어긋날 여지가 없습니다.
- **로비와 여러 방**: 누구나 방을 만들 수 있고(방 이름 선택), 로비에는 방 목록과 상태(대기 중/대국 중, 참가자)가
  보입니다. 방마다 좌석 두 개, 대국, 채팅이 따로 있습니다. 주소 `?room=<id>`가 곧 초대 링크입니다. 대국이 없고
  아무도 없는 방은 10분이 지나면 로비를 읽을 때 정리됩니다. 방은 최대 50개입니다.
- **상태는 JSON 레코드로 저장**됩니다(`model.ts`). 대국은 수 목록(UCI)과 시계 상태로 저장하고, 국면·기보·반복
  판정은 수를 다시 재생해 복원합니다(인스턴스별 캐시 사용).
- **모든 변경은 순수 함수**입니다(`logic.ts`: 방 레코드 + 입력 + 시각 → 새 방 레코드 또는 오류 코드). 저장소는
  낙관적 동시성 제어로 적용하므로(`Store.updateRoom`: 충돌 시 최신 상태로 다시 계산), 같은 방에 두 인스턴스가
  동시에 요청을 받아도 한쪽 변경이 사라지지 않습니다.
- `service.ts`는 게임 상태를 들고 있지 않습니다. 이 인스턴스의 연결 목록과 타이머만 가지므로, 인스턴스가 몇 개든
  같은 방을 함께 처리할 수 있습니다.
- 규칙 엔진(`src/shared/chess`)과 시계(`src/shared/clock.ts`)는 순수 함수라 서버와 클라이언트가 같은 코드를
  씁니다. 클라이언트는 합법 수 표시, 승진 여부, 시계 표시에만 쓰고 판정은 항상 서버가 합니다.
- 클라이언트는 `view-model.ts`의 순수 함수가 (스냅샷 + 로컬 UI 상태 + 서버 시각)에서 화면에 필요한 모든 값을
  계산하고, `main.ts`는 그 결과를 DOM에 반영합니다.

## 프로토콜

타입 정의: [`src/shared/protocol.ts`](../src/shared/protocol.ts)

클라이언트 → 서버 요청(모두 acknowledgement로 `{ ok: true }` 또는 `{ ok: false, error }` 응답):

| 이벤트              | 인자                             | 설명                                                       |
| ------------------- | -------------------------------- | ---------------------------------------------------------- |
| `profile:set-name`  | `name`                           | 이름 변경                                                  |
| `lobby:enter`       | –                                | 로비 구독(방에서 나옴). 서버가 `lobby` 스냅샷을 보냄       |
| `room:create`       | `name` (빈 문자열이면 기본 이름) | 방 만들기, 응답에 `roomId`                                 |
| `room:join`         | `roomId`                         | 방 입장(관전자로). 서버가 `room` 스냅샷을 보냄             |
| `room:sync`         | –                                | 시계가 0이 되는 등 시간 규칙이 적용될 때가 되면 판정 요청  |
| `seat:take`         | –                                | 참가. 두 번째 참가자가 앉으면 대국 시작(흑백 무작위)       |
| `seat:leave`        | –                                | 참가 취소                                                  |
| `game:move`         | `{ from, to, promotion?, ply }`  | 수. `ply`는 클라이언트가 본 수의 개수(중복·지연 요청 방지) |
| `game:resign`       | –                                | 기권                                                       |
| `game:offer-draw`   | –                                | 무승부 제안(상대가 이미 제안했다면 합의)                   |
| `game:accept-draw`  | –                                | 상대의 제안 수락                                           |
| `game:decline-draw` | –                                | 상대의 제안 거절                                           |
| `chat:send`         | `text`                           | 방 채팅                                                    |

서버 → 클라이언트: `session`(토큰·공개 id·이름), `lobby`(방 목록), `room`(방 전체 스냅샷, 서버 시각 포함).

오류 코드와 한국어 메시지는 [`src/client/text.ts`](../src/client/text.ts)에 있습니다.

## 세션과 재접속

- 클라이언트는 첫 접속 때 서버가 준 **세션 토큰**을 `sessionStorage`에 저장하고, 재연결·새로고침 때 핸드셰이크
  `auth`로 보냅니다. 세션은 저장소에 있으므로 어느 인스턴스에 다시 붙어도 같은 플레이어로 이어집니다. 탭마다 별도
  저장소이므로 탭 두 개는 서로 다른 플레이어입니다.
- 다시 연결되면 클라이언트가 현재 화면(로비 또는 `?room=`의 방)에 다시 들어가고, 최신 스냅샷을 받습니다.
- 방송되는 스냅샷에는 공개 id만 들어가고 토큰은 본인에게만 전달됩니다.
- 이름은 `localStorage`에 기억해 다음 방문 때 다시 묻지 않습니다(원본은 매번 `prompt()`로 물었습니다).

## 접속 기록, 시간 처리와 연결 끊김

- **접속 기록(presence)**: 각 인스턴스가 자기 연결을 15초마다 저장소에 기록합니다. 40초 동안 갱신이 없는 연결은
  끊긴 것으로 보므로, 인스턴스가 비정상 종료돼도 "접속 중"으로 남지 않습니다.
- **시계**: 각자 **15분 + 수마다 10초 추가(피셔 방식, 누적)**입니다. 계산은 `src/shared/clock.ts`의 순수 함수로
  되어 있어 서버의 판정과 클라이언트의 표시가 같은 식을 씁니다. 원본(한 수당 3분)은 각 클라이언트가 시간 초과를
  _스스로_ 신고했기 때문에, 조작된 클라이언트는 시간 초과로 지지 않을 수 있었습니다.
- **시간 규칙은 "읽을 때 판정"**합니다(`logic.resolve`): 시간 초과, 연결 끊김 기권패, 대기 좌석 해제는 방을 읽거나
  바꿀 때마다 그 시각 기준으로 적용되고, 실제로 일어난 시각에 시계를 멈춥니다. 여기에 더해 (1) 요청을 처리한
  인스턴스가 다음 기한에 로컬 타이머를 걸고, (2) 클라이언트도 화면의 시계·카운트다운이 0이 되면 `room:sync`를
  보냅니다. 특정 인스턴스의 타이머가 사라져도(Vercel 함수 종료 등) 판정이 누락되지 않습니다.
- **연결 끊김**: 대국 중 연결이 끊겨도 시계는 계속 흐르고(FIDE 온라인 규정 11.4), **60초 안에 돌아오지 않으면
  기권패**입니다(11.4.2는 재접속 허용 시간을 대회 규정이 정하도록 함. 상대가 체크메이트할 수 없는 기물이면 무승부).
  상대 화면에는 남은 시간이 표시됩니다. 두 플레이어가 모두 나가도 대국이 끝나므로 방이 막히지 않습니다.
- 대국 시작 전 좌석에 앉은 사람의 연결이 끊기면 새로고침을 고려해 15초 동안 자리를 유지합니다.

## 보안과 입력 처리

- 모든 이벤트 인자는 `src/server/validation.ts`에서 형식·범위를 확인하고, 맞지 않으면 `invalid-payload`로 거부합니다.
  원본의 이벤트(`gameend`, `movefinish` 등)는 핸들러가 없어 무시됩니다.
- 채팅·이름은 제어 문자와 보이지 않는 서식 문자(양방향 재정의, 폭 없는 공백 등)를 제거하고 길이를 코드 포인트로
  제한합니다(이름 16자, 채팅 200자). 화면에는 항상 `textContent`로만 넣으므로 HTML로 해석되지 않습니다.
- 채팅 작성자는 서버가 붙입니다. 원본은 클라이언트가 보낸 객체를 그대로 방송해 `type`·접속자 수 같은 필드를
  위조할 수 있었습니다.
- 요청 제한: 소켓당 초당 20개 이벤트, 채팅 10초에 5개, 방 만들기 분당 3개, 주소당 분당 새 연결 30개
  (`CONNECTIONS_PER_MINUTE`로 조정). 메시지 최대 16KiB. 방은 최대 50개.
- 페이지와 소켓이 같은 출처이므로 CORS를 열지 않습니다(원본은 `origin: '*'`). 정적 응답에 CSP, `nosniff`,
  `Referrer-Policy`, `Cross-Origin-Opener-Policy` 헤더를 붙이고 `X-Powered-By`를 끕니다.
- 인증이나 계정은 없습니다. 이 앱은 친구끼리 한 서버에서 두는 규모를 전제로 하며, 공개 인터넷 운영을 위한
  인프라(HTTPS 종단, 프록시 뒤 실제 IP 판별 등)는 범위 밖입니다.
